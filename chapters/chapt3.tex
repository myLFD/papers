\chapter{需求分析}
本章节围绕安卓图形系统展开需求分析，从需求导出、功能性需求以及非功能性需求对系统进行分析。

\section{需求导出}
\subsection{SurfaceFlinger关键服务分析}
Android图形系统作为移动端计算机的核心子系统，构建了从应用程序界面到物理显示设备的完整视觉呈现管道。
这个复杂的系统包含超过50个核心组件，其中SurfaceFlinger作为系统级的合成引擎，承担着最核心的图形处理任务，保障其正确运行是图形系统运行的关键。
整个系统的运作可以分解为三个层次架构：应用层、图形处理层和硬件抽象层。
应用层负责通过UI框架构建图形界面元素，图形处理层包括渲染引擎和合成器引擎，硬件抽象层主要是为这两个引擎提供支持。
本文的主要工作主要是硬件抽象层的实现。
而渲染引擎和合成器引擎作为SurfaceFlinger服务的核心功能，分析这两个引擎的作用和依赖有助于引出硬件抽象层的需求，下面对这两个引擎进行简要分析。

渲染引擎分析：渲染引擎是负责将抽象的图形描述转化为最终可视像素的软件系统。Android渲染引擎默认使用的是Skia，
在SurfaceFlinger初始化过程中，会创建一个线程专门用于Skia引擎的初始化并用于后续的图形绘制，
在SkiaGLRenderEngine::create时，会依次执行eglGetDisplay获取EGL显示句柄，此句柄代表了要渲染的物理设备；eglInitialize初始化EGL环境，并获得EGL的主次版本号；
eglQueryString查询与当前显示连接相关的字符串信息，包括EGL版本信息、供应商版本信息以及支持的客户端API等，安卓还会使用EGL\_EXTENSIONS
获取有关安卓特性的拓展并初始化；使用createEglContext在EGL中创建 OpenGL ES 上下文；然后使用eglMakeCurrent将指定的渲染上下文和表面设置为当前的函数。
因此渲染引擎的正常运行需要OpenGL ES相关实现支持。

合成器引擎分析：SurfaceFlinger中集成了合成器引擎CompositionEngine，也是SurfaceFlinger的核心部分，负责将多个图层按照z轴顺序合成并渲染等。
其作为硬件混合渲染器的客户端，会通过跨进程通信的方式调用框架中的Icomposer实现和接口，从而完成与具体硬件混合渲染器的交互。因此合成器引擎需要硬件混合渲染器实现的支持。
而合成器在合成图像时需要向系统申请图形缓存，因此也需要图形内存缓存分配的实现。

由上，为了实现对SurfaceFlinger的支持，需要实现OpengGL ES对渲染引擎提供硬件支持，以及实现硬件抽象层中的Gralloc和HWC服务为合成器引擎提供硬件支持。 

\subsection{架构差异分析}
\label{sec:架构差异分析}
本课题需要在LoongArch架构下实现，而Android多应用于ARM架构，ARM与LoongArch架构的图形系统有较大差异，具体表现为ARM架构下的MaliGPU以及多数手机SOC集成的GPU
没有独立显存\cite{Inki2011}，而在LoongArch的内核中，是使用DRI框架来调用GPU，并且GPU有自己的独立显存。
对LG110内存模型进行分析，LG110内存架构采用分层设计如图\ref{fig:LG110内存模型}所示，包含GPU本地VRAM和系统主存中的GTT内存模块。
其实现原理体现为：GPU的VRAM通过PCI总线直接映射至CPU的地址空间，允许CPU通过标准PCIe协议直接访问这部分显存资源；
而GTT内存作为动态管理区域，借助页表机制将系统物理内存映射到虚拟地址空间，需经MMU转换后才能被访问。
就GPU端的数据访问逻辑而言，其采用分级的页表管理策略。针对本地VRAM区域，页表项直接记录该存储块的物理地址，使得GPU可直接基于物理地址进行存取操作；
而对于映射至系统主存的GTT区域，页表项存储的是经过DMA引擎转换后的设备地址，因此可以根据DMA的地址发起 DMA 请求获取数据。

  \centering
  \includegraphics[width=0.8\textwidth]{LG110内存模型.pdf}
  \caption{LG110内存模型}
  \label{fig:LG110内存模型}
\end{figure}

因此，首先需要解决的是在LoongArch架构下，Android系统中显存和系统内存分配映射的问题。AndroidX86\cite{AndroidX86}
很大程度上解决这个问题，该项目使用Mesa作为OpenGL ES实现，基于DRM和GEM实现了Gralloc模块，成功的在x86架构下运行SurfaceFlinger并实现硬件加速\cite{XTYY201710015}。
基于这个思路，本课题也可以采用Mesa作为OpenGL ES实现以及Mesa提供的GBM（General Buffer Manager）来管理缓冲区，
为此需要LoongArch架构的DRM框架和用户态libdrm的支持。其中DRM框架需要基于安卓通用内核5.10实现。

\subsubsection{硬件功能支持}
缓冲区分配与管理功能构成了整个系统运行的基础，其核心职责是为上层图形框架和硬件模块提供统一、高效、跨平台的图像缓冲区资源。
统一的缓冲区管理可以避免内存碎片，解决冗余数据拷贝和跨模块接口等问题，可以提升图形数据处理效率与系统整体性能。其功能包括缓冲区的创建、销毁、导入、映射、解除映射等核心功能。
% 同时在分配时可基于多个关键维度进行决策，包括图像格式、分辨率、使用场景，以及平台后端。
缓冲区管理需要具备兼容龙芯LG系列GPU的后端机制，系统需要根据不同版本的GPU抽象出buffer object分配逻辑，保证核心接口一致性的同时保留添加新特性的能力。
% 现代图形栈中，各个硬件模块往往由不同的驱动控制，并在用户空间有独立的处理流程。为实现模块间的高效协作，需要一种安全、高效的机制来在进程之间、驱动之间共享图像缓冲区。
而在缓冲区共享功能下，缓冲区被一旦分配成功，它就必须具备被导出给其他使用者的能力。这要求系统能将缓冲区封装为一种可识别、可传递、可管理的资源对象。
在 Linux 图形系统中，DMA-BUF是事实上的共享内存标准，系统需要将自身内部的缓冲区对象导出为一个 DMA-BUF 文件描述符，导出的 FD 可以通过标准UNIX机制传递给其他用户空间模块。
而导出的缓冲区不仅仅是一个裸文件描述符，系统还需要一套详细的元信息描述机制，需要配合尺寸、格式、每行字节跨度（stride）、plane 分布、对齐要求等参数信息。
而在缓冲区共享功能要求的同时，需要支持生命周期管理与引用追踪。在多进程系统中，一个缓冲区可能被多个模块同时使用，它的释放必须延迟到所有使用者均释放之后。
因此需要一个引用计数机制，对缓冲区导入导出时确定生命周期，避免出现资源泄露的风险。最后在功能设计上还需要考虑共享后的缓存一致性与同步功能。
另外适配DRM/KMS接口，正确处理IOCTL命令，通过drmIoctl和DRM内核子系统交互，并且支持GSGPU的缓冲区。
% 按照GBM接口标准，应有如下表\ref{tab:硬件功能支持用例表}所示功能。

\section{非功能需求}

\subsection{兼容性}
\label{p:兼容性}

驱动内核层需要对接硬件底层功能接口，主要是对图形内存对象管理的IOCTL命令进行封装，包括支持处理上下文、命令流、内存映射、调用等核心功能。
另外龙芯平台的 GSGPU 驱动当前处于闭源状态，尚未主线合入内核源码树。而在此情况下，内核版本的更迭，特别是在图形领域的DRM模块，接口常常因为硬件特性的变化而变动。
因此，需要兼容Linux内核版本4.19/5.10以及libdrm。具体来说就是要在不同内核平台下构建同一驱动，加载并通过设备和libdrm相关测试。
同时为了兼顾模块化的需求，驱动应以内核模块形式构建（可通过 modprobe/rmmod 加载卸载）。

% 同时保证 SurfaceFlinger 与composer HAL之间的调用接口稳定，不破坏 CTS要求。
% 同时，需要支持龙芯 LG 系列 GPU 的显存管理架构，特别适配VRAM 与 GTT 双域内存结构。

% 2.OpengGL ES由用户态驱动Mesa实现，主要为安卓图形系统的Skia绘图引擎提供图形编程接口支持。因此在构建OpenGL ES支持后，应对图形编程接口进行兼容性测试，也就是

\subsection{稳定性​}

1.内核驱动模块化构建：内核驱动应以模块形式构建（可通过 modprobe/rmmod 加载卸载），确保模块初始化和退出流程健壮。
在龙芯3A5000处理器以及7A2000桥片真机环境下，持续稳定运行时间超过48H，运行期间内核日志无Oops、Panic、BUG等崩溃类错误以及WARN\_ON、WARNING、BUG\_ON等严重警告错误，
且可以连续加载卸载模块的次数超过50次，在加/卸载期间同样无严重日志警告错误。

2.合成器异常恢复及容错：支持 DRM Master 丢失后的重新绑定逻辑，自动恢复显示状态。对 Connector 熄灭等异常进行检测与恢复。
同时支持超时与故障告警机制，防止系统卡死或死循环。同时应当多个输出通道独立运行，任一通道故障不影响其他显示输出。

3.缓存分配应确保不同进程的缓冲区访问权限隔离以实现内存隔离，缓冲区对象需通过引用计数自动释放以抗内存泄漏。

\subsection{性能需求}

1.​缓冲区分配​性能：在龙芯3A5000处理器、7A2000桥片和内存8GB真机环境下（后续称为龙芯安卓系统环境），运行Android Naive OpenGL ES程序时，去除预热时数据，
在进入渲染交换稳定状态之后针对4B大小的像素格式带宽达到2.5Gb以上，每秒可以分配不低于250个缓冲区，在2B像素格式下带宽达到5Gb以上，每秒可以分配不低于300个缓冲区。
%缓冲区分配延迟、 缓冲区导出时间、CPU映射开销等核心实现为主要需求，其中缓冲区分配延迟平均时间不超过0.5ms，95\%的延迟时间不超过0.8ms，最大延迟不超过1ms，缓冲区导出平均时间不超过0.1ms，95\%的延迟时间不超过0.3ms，
% 而CPU映射操作平均耗时不超过0.5ms。

2.GPU图形吞吐能力与命令提交效率要求：在龙芯安卓系统环境下，基于gl2\_perf测试以常见着色器以及纹理类型为运行前提，MPPS性能体现了GPU 像素填充带宽，
在1080p 分辨率、默认帧缓冲格式（RGBA8888）下，最低MPPS不低于1000，DC60不低于10。
